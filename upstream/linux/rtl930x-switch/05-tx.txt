net: ethernet: realtek: rtl9300: transmit frames

Frames to send go through TX ring 0 of the DMA engine. Each descriptor
carries a CPU tag with forwarding type "physical", which sends the frame
to the ports of its destination mask without an L2 lookup and regardless
of the spanning tree state, so it reaches exactly the port the frame is
for. The engine sends the FCS in place of the last four bytes of the
buffer, as OpenWrt's driver shows when it reuses the bytes of its DSA
tag for that, and only reads the buffer. So the buffer takes them from
the tailroom, which is zeroed where the frame owns its buffer; a clone
shares its buffer, so there they stay as they are. Only frames shorter
than the minimum are padded, and frames longer than the switch takes are
dropped.

The TX done interrupt schedules the NAPI context, which frees the frames
the hardware has sent. OpenWrt unmasked the TX done interrupts from 2021
until January 2026 but only acknowledged them, as it copies the frames
it sends, and that bit 0 is TX ring 0 is inferred from the RX registers,
which have a bit per ring. While frames are in the ring, a timer
therefore also kicks the engine and the NAPI context every tick, as
stmmac's TX coalescing timer does, so that sent frames are freed in time
whether the interrupt comes or not, and a lost trigger doesn't leave
frames in the ring.

A transmit is triggered by writing the control register as a whole,
not by reading it back and setting the trigger as OpenWrt's driver
does: its reads sometimes come back empty, and writing such a value
back would stop the engine.
